------------------------------------------------------------------------------
WHY
------------------------------------------------------------------------------
A cache line is 64 bytes, so it holds 8 float64 values.
The hardware never loads one number; it loads the whole line.

Mode A walks a row. Addresses advance by 8 bytes, so one line
load serves the next 8 reads. Of the 64 bytes pulled from RAM, all
64 are used. The hardware prefetcher also recognises the
straight-line pattern and starts fetching ahead, so the core rarely
waits at all.

Mode B walks a column. Consecutive reads are one full row apart:
8,000 elements x 8 bytes = 64,000 bytes. Every read
therefore lands on a new cache line, and only 8 of the 64 bytes
fetched are ever used before the line is evicted. That is 87.5% of
the memory bandwidth spent moving bytes nobody reads, and it predicts
a penalty of about 8x from bandwidth waste alone.

Measured penalty was 11.89x.
That is worse than the 8x bandwidth argument predicts, which is
expected. The stride also defeats the prefetcher, and with a row
stride of 64,000 bytes each access tends to fall in a
different memory page, so the TLB misses as well. Cache misses,
failed prefetch and TLB pressure compound.

The practical rule: iterate in the order the array is stored. In C,
C++, Python/NumPy and Java that is row-major, so the rightmost index
belongs in the innermost loop. In Fortran, MATLAB and Julia the
storage is column-major and the rule inverts. Getting this backwards
costs an order of magnitude and changes nothing about the output.
