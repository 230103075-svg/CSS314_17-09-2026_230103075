1. WHY THE NAIVE LOOP CANNOT BE USED
------------------------------------------------------------------------------
`for _ in range(n): arr[i] += 1`, 50,000,000 iterations, 1 thread
  wall time         : 0.005 ms
  per iteration     : 0.0001 ns
  counter value     : 50,000,000  (correct)

A single load-modify-store to L1 cache costs roughly 1 ns. A figure
far below that means the loop never ran: LLVM recognised the closed
form and replaced 50 million increments with one addition. The result
is still correct, but nothing was measured. Every benchmark below
therefore uses a loop-carried dependency that forces a genuine load
and store on each iteration.

5. ANALYSIS
------------------------------------------------------------------------------
All three variants perform exactly the same arithmetic and each
thread touches only its own counter. There is no lock, no logical
sharing and no race. The only difference between A and B is the
distance in bytes between the counters.

Cache coherence works on whole cache lines, not on variables. In A
all counters sit inside one 64-byte line, so under MESI each write
must take that line into the Modified state, which invalidates every
other core's copy. The next core to write takes a HITM miss and pulls
the line back. The line ping-pongs between cores for the whole run
even though no core ever wants another core's data. That is false
sharing: the hardware shares a line, the program shares nothing.

B spaces the counters 64 bytes apart, so each core owns its own line
outright and never has to give it up. C goes further and keeps the
counter in a private buffer, touching shared memory once per thread.

Measured here: the unpadded version is 1.90x slower,
which is the coherence traffic made visible.

Practical remedies, in the order one should reach for them:
  1. Keep the hot counter thread-local and publish once (variant C).
  2. Pad shared slots to a full cache line: alignas(64) in C++,
     @Contended in Java, CachePadded in Rust, _ [56]byte in Go.
  3. Use a reduction instead of a shared array when the final value
     is all that matters.
