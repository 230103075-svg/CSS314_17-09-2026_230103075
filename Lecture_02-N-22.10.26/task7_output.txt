>>> KERNEL A (the vector copy) STALLED IN SCALING.
>>> Its bottleneck is memory channel saturation, not the CPU.

Kernel A does zero arithmetic per element, so every core spends
its entire time waiting on the memory bus. One core already pulls
21.53 GB/s; adding 11 more only reaches 47.59 GB/s, because
they are all queueing at the same memory controller. The extra
cores are idle inside a stall, which is why efficiency fell to
18.42%.

Kernel B moves exactly the same 16 bytes per element, but each
element also costs three transcendental evaluations. That work
happens in the core's own execution units, which are private and
therefore scale: efficiency held at 59.28%.

------------------------------------------------------------------------------
ARITHMETIC INTENSITY — WHY THE TWO DIFFER
------------------------------------------------------------------------------
Arithmetic intensity is flops performed per byte moved from memory.
It is the number that decides which ceiling a kernel hits.

  Kernel A : 0 flops / 16 bytes = 0.00 flops per byte
             Nothing is computed. The kernel is a pure bandwidth test
             and sits on the sloped part of the roofline, where
             performance is bandwidth x intensity and nothing else.

  Kernel B : ~3 transcendental calls / 16 bytes
             sin, cos and tan each cost on the order of tens to
             hundreds of cycles. Intensity is high enough that the
             kernel sits on the flat part of the roofline, limited by
             the cores' arithmetic throughput, which grows with core
             count because each core has its own execution units.

The memory controller is shared; execution units are not. That is the
whole reason the two kernels scale differently, and it is why Amdahl's
Law alone cannot predict parallel performance: it models serial
fractions, not contention for a shared resource.
