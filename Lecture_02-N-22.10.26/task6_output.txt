ANALYSIS
------------------------------------------------------------------------------
The increment is not one operation. It is read the value, add one,
write it back. If a second thread reads between another thread's read
and its write, both compute the same new value and one increment
vanishes. Nothing crashes and no error is raised; the number is
simply wrong, which is what makes this class of bug dangerous.

Runs A and B both finished at exactly 8,000,000, even with the
switch interval cut by a factor of 5000. That is not because the
code is correct. It is because CPython's GIL lets only one thread
execute bytecode at a time, and on Python 3.14.0 the interpreter
does not take a switch in the middle of this particular
read-modify-write. The bug is fully present in the source; the
interpreter is simply standing in front of it.

This is worth stating plainly because it is the trap: the same
logic ported to a language without a GIL, or run on a free-
threaded Python build, starts losing data immediately. Relying on
the GIL for correctness means the code is one runtime change away
from silently producing wrong numbers.

Run C lost 46.5344%. With the GIL gone, four cores perform
genuine simultaneous read-modify-write on one memory location and
most of the work is overwritten. This is the unmasked hardware
behaviour that the GIL was concealing in A.

D fixes it with a mutex: one thread at a time holds the lock, so the
read-modify-write becomes indivisible and the count is exact. The
price is in the summary above. The lock serialises the hot path, so
the four threads no longer overlap on it at all.

E is the better fix where it applies. Each thread counts in a private
variable with no contention, and the four partial results are merged
once at the end. Correct like D, but without serialising anything.
This is what OpenMP's reduction(+:x) does, and it is why a reduction
should be preferred over a shared counter whenever the intermediate
value is not actually needed.
