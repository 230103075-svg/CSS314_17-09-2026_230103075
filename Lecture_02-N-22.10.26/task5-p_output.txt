ANALYSIS
==============================================================================
Variant A best speedup : 1.0862x at pool 256
Variant B best speedup : 7.4506x at pool 24

Variant A never scaled. SHA-256 over 1 KB stays inside the GIL,
so only one thread executes at a time regardless of pool size.
Adding threads cannot add throughput; it only adds contention for
the lock and work for the scheduler. This is the measurement the
task asks for, and the flat-then-worsening curve is the correct
result for it, not a failed experiment.

Variant B removes the lock and the curve appears:
  it climbs to 7.45x at pool 24, close to the 8 physical
  cores available, and then flattens or falls.

The oversubscription threshold is pool size 48. Past the optimum
of 24, every extra thread is a thread that must be scheduled onto
a core that is already busy. The costs that appear are:
  - context switches: the OS saves and restores register state,
    and each switch costs microseconds of pure overhead.
  - cache pollution: a thread resuming on a different core finds
    its working set cold and reloads it from memory.
  - scheduler work: the run queue grows and the kernel spends
    more of its own time deciding what to run next.
  - memory: each thread carries its own stack, so a 256-thread
    pool reserves hundreds of megabytes of address space for
    threads that are mostly waiting.

The practical rule this measures: for CPU-bound work, size the pool
to the core count, not to the task count. 10,000 tasks do not need
10,000 threads. Threads are a way to use cores, and once the cores
are busy more threads only add bookkeeping. Oversubscription pays off
only for I/O-bound work, where threads spend their time blocked and
a waiting thread costs nothing but memory.
