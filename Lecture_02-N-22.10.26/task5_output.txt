4. PREDICTED CROSSOVER FROM FIRST PRINCIPLES
------------------------------------------------------------------------------
Per-element serial cost c  : 1.6399 ns (from N = 10,000,000)
Dispatch overhead O        : 290.452 us
Workers p                  : 12

N* = O / (c * (1 - 1/p)) = 193,219 elements

That model assumes the parallel part scales perfectly by p.
It does not: this kernel reads 8 bytes and writes 8 bytes per
element while doing two flops, so past the cache it is limited
by memory bandwidth, not by core count. Real scaling is lower
than p, which pushes the true crossover ABOVE this estimate.
Treat N* as a lower bound.

------------------------------------------------------------------------------
5. ANALYSIS
------------------------------------------------------------------------------
At small N the array fits in cache and the whole kernel finishes
in less time than it takes to hand work to the pool and collect
the results. The thread pool is pure loss: the speedup column
sits far below 1.0 and the parallel column is nearly flat,
because what is being timed is dispatch, not arithmetic.

As N grows the arithmetic starts to dominate that fixed cost. The
parallel time grows roughly N*c/p against the serial N*c, so the
two curves converge and then cross. Past the crossover the fixed
overhead is amortised over enough elements to stop mattering.

The gain does not keep growing with core count. y = a*x + b does
two floating-point operations per 16 bytes moved, so once the
array leaves cache every core is waiting on the same memory
controller. That is a roofline ceiling, and it is why the speedup
at the largest N is far below the worker count.

Practical reading: splitting an array across cores is only worth
it once the work per call clears the dispatch cost measured in
section 1. Below that threshold the correct optimisation is to
stay on one thread.
